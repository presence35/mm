Phase 4: accessibility audit, deploy docs, and the sync bugs it surfaced

Measured, not asserted. A browser audit across screens found 32px chips and
36px small buttons below the 48px target the contract requires, and chips
clipping their own labels at 200% text scale. Fixed by expanding the hit
area outside the visual rather than inflating the control, which keeps the
density M3 asks for, and by making chip height and width floors instead of
fixed sizes. Re-audited: zero violations, no clipping at 200% text, no
horizontal scroll.

Verifying sync in a live browser surfaced five real defects:

- booleans from a JS client cannot bind to SQLite, so wrap_required: false
  crashed the server process. bindable() coerces, and a non-scalar becomes
  JSON rather than taking the server down.

- boathouse_no, slip_no, storage_row and season_year were declared TEXT, so
  SQLite round-tripped 3 as "3.0". That rendered as "BH 3.0" and, once
  pulled onto a client, kept reproducing itself. Now INTEGER, and reads
  normalise so a legacy row cannot perpetuate the bad value.

- hydrate() was guarded by a boolean checked before any await, so Boot and
  SyncProvider both seeded on mount. The snapshot queued twice and produced
  36 conflicts against our own data. Now memoised on the promise.

- notifyLocalWrite entered "syncing" unconditionally, so each cycle's own
  reload re-triggered it and the machine never settled. The data was
  correct; the state was not. Now only on actual pending work.

- seed rows were stored but never queued, so the first edit pushed rev 1
  against a row the server had never seen and became a conflict instead of
  an insert. The bootstrap snapshot now creates the marina on a new server,
  and pull drops ops the server has already superseded so a second device
  seeding the same snapshot does not fight itself.

30 tests. Clean run against a fresh database and a fresh device: 12 ops
applied, 0 conflicts, integers intact.
